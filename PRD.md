# DrawArch MCP — Product Requirements Document

**Status:** V1 retained; V2 reference-recreation amendment implemented  
**Version:** 2.0  
**Date:** 2026-08-14  
**Owner:** Product team  
**Authority:** This file is the single source of truth for product scope, behavior, acceptance criteria, and release boundaries. Implementation plans and code must reference this document and must not redefine requirements elsewhere.

## 1. Product Summary

DrawArch MCP is a Model Context Protocol server that enables an AI agent to generate polished, animated, natively editable diagrams.net architecture diagrams. Its primary artifact is a self-contained `.drawio` file in which every component, SVG/image, label, container, and connector remains independently editable.

The visual quality target is a presentation-ready architecture illustration: themed canvas, clear subsystem grouping, real SVG/icon assets, readable hierarchy, orthogonal colour-coded paths, and animated connectors that communicate direction.

## 2. Problem

Existing AI diagram generation commonly produces one of three inadequate outputs:

1. Flattened images that cannot be meaningfully edited.
2. Generic diagrams made from plain boxes and inconsistent icons.
3. Editable diagrams with weak architecture semantics, poor routing, overlaps, and no clear datapath language.

Users need an agent-accessible tool that produces professional diagrams without giving up native diagrams.net editing.

## 3. Goals

V1 must:

- Generate a valid native `.drawio` file from a structured architecture description supplied by an MCP host/LLM.
- Keep all nodes, groups, labels, assets, and connectors independently editable.
- Support selectable visual themes without changing architecture semantics.
- Use real SVG/icon assets rather than emojis or AI-generated placeholder artwork.
- Resolve assets from both a bundled curated catalogue and approved online SVG sources.
- Embed resolved assets into the `.drawio` file so it remains portable offline.
- Support deterministic layouts suitable for architecture diagrams.
- Support colour-coded animated connectors with direction, labels, timing, and flow categories.
- Validate the generated file and return actionable warnings or errors.
- Run locally over MCP stdio with no mandatory cloud service.

## 4. Non-Goals for V1

V1 will not:

- Inspect a GitHub repository or codebase to infer its architecture.
- Generate architecture semantics directly from source code.
- Provide multi-user collaboration, accounts, billing, or hosted persistence.
- Reproduce proprietary assets without permission.
- Use generative raster imagery as a normal architecture icon source.
- Guarantee pixel-identical rendering across every diagrams.net release.
- Implement a standalone graphical editor; diagrams.net remains the editor.

## 5. Target Users

- Software and solution architects
- Developers creating system-design documentation
- Students and educators creating project architecture diagrams
- IoT, robotics, ML, and cloud teams needing real component imagery
- Consultants and technical writers producing presentation-ready diagrams

## 6. Primary User Journey

1. The user asks an MCP-capable AI agent for an architecture diagram.
2. The agent translates the request into DrawArch's structured architecture schema.
3. The agent selects a layout, theme, and asset mode.
4. DrawArch validates the specification.
5. DrawArch resolves each node's asset from the bundled catalogue, then approved online sources when required.
6. DrawArch calculates deterministic positions and connector waypoints.
7. DrawArch generates a self-contained native `.drawio` file.
8. DrawArch validates the generated document and returns the output path plus warnings and a generation summary.
9. The user opens the file in diagrams.net, where connectors animate and every element remains editable.

## 7. V1 MCP Tools

### 7.1 `list_themes`

Returns the available theme identifiers, descriptions, backgrounds, and intended uses.

### 7.2 `list_assets`

Searches the bundled asset catalogue by text, tag, category, or provider.

### 7.3 `resolve_asset`

Resolves an asset using the configured fallback chain. It can return bundled assets immediately or query an online provider when enabled.

### 7.4 `create_drawio`

Validates an architecture specification, resolves its assets, lays it out, renders it to diagrams.net XML, writes the `.drawio` file, validates the result, and returns a summary.

### 7.5 `validate_drawio`

Validates a `.drawio` file generated by or supplied to DrawArch. It reports malformed XML, missing IDs, dangling connector references, unembedded remote images, unsupported themes, and duplicate cell IDs.

## 8. Architecture Specification

The host LLM supplies structured data. DrawArch does not depend on an internal LLM and does not ask an LLM to write raw diagrams.net XML.

```json
{
  "title": "Real-Time IoT Safety Platform",
  "theme": "animated-sketch-dark",
  "layout": "edge-cloud",
  "outputFile": "iot-safety.drawio",
  "groups": [
    { "id": "edge", "label": "Edge Devices" },
    { "id": "cloud", "label": "Cloud Platform" }
  ],
  "nodes": [
    {
      "id": "phone",
      "label": "Mobile Device",
      "groupId": "edge",
      "asset": "mobile-device",
      "subtitle": "GPS + IMU"
    }
  ],
  "edges": [
    {
      "id": "telemetry",
      "source": "phone",
      "target": "broker",
      "label": "MQTT telemetry",
      "flow": "realtime",
      "animated": true
    }
  ]
}
```

### 8.1 Required invariants

- IDs are unique within their respective collections.
- Each node belongs to zero or one group.
- Every referenced group, source node, and target node exists.
- An edge cannot connect a node to itself in V1.
- Labels are non-empty after trimming.
- Output names end in `.drawio` and cannot escape the configured output directory.
- Unsupported themes, layouts, flow types, and asset modes are rejected.

## 9. Themes

V1 includes these themes:

1. `animated-sketch-dark` — black canvas, sketch treatment, dotted rounded groups, colourful animated paths.
2. `animated-sketch-light` — light canvas equivalent of the sketch style.
3. `professional-cloud` — restrained cloud-architecture styling.
4. `minimal-corporate` — presentation-friendly neutral styling.
5. `technical-blueprint` — blueprint grid-inspired technical styling.
6. `presentation-neon` — dark high-contrast presentation styling.

Themes are token sets. They control canvas, typography, group containers, node cards, label colours, shadows, sketch treatment, and connector styling. Themes do not add, remove, or reconnect architecture components.

## 10. Layouts

V1 supports:

- `horizontal` — left-to-right architecture flow.
- `vertical` — top-to-bottom architecture flow.
- `edge-cloud` — group-oriented edge/gateway/cloud/user arrangement.
- `hub-spoke` — one central service with surrounding dependants.
- `pipeline` — ordered stages with supporting systems arranged below.

Layout requirements:

- Deterministic output for identical inputs.
- Minimum spacing between node bounds.
- Group bounds expand to contain their children and labels.
- Prefer orthogonal connectors.
- Add waypoints when required to reduce intersections with nodes.
- Preserve readable labels at normal zoom.
- Generate a legend when more than one flow category is used.

## 11. Asset System

### 11.1 Asset requirements

- SVG is preferred; PNG is permitted only when SVG is unavailable.
- Emojis are not permitted as architecture assets.
- Assets must remain movable and resizable as individual diagrams.net image cells.
- Remote assets must be embedded as data URIs before the `.drawio` file is returned.
- SVG content must be sanitized before embedding.
- External scripts, event handlers, foreign objects, and unsafe links are rejected.
- Each asset record stores stable ID, title, category, provider, tags, source URL when applicable, licence metadata, media type, and integrity hash.

### 11.2 Resolution chain

1. Exact bundled asset ID.
2. Bundled alias, tag, category, or semantic match.
3. Approved online provider search when online resolution is enabled.
4. Generic bundled asset for the requested category.
5. Actionable failure if no safe asset or fallback exists.

### 11.3 V1 bundled catalogue

V1 ships a small coherent SVG starter pack covering:

- User
- Mobile device
- Web application
- API/service
- Server
- Database
- Message queue
- Object/file storage
- Cloud
- AI/model
- Sensor/IoT device
- Monitoring

The catalogue format is extensible so official AWS, Azure, Google Cloud, Kubernetes, Docker, database, and hardware packs can be added without changing the renderer.

### 11.4 Online provider

V1 provides an Iconify-compatible online resolver with configurable base URL and network timeout. Online lookup is opt-in at server runtime. Results must be sanitized and embedded; the output never contains a hotlinked runtime dependency.

## 12. Connector and Animation System

Connectors must support:

- Source and target node bindings
- Arrow direction
- Orthogonal waypoints
- Label
- Flow category
- Colour
- Solid, dashed, or dotted pattern
- Animation enabled/disabled
- Flow duration
- Flow timing
- Flow direction

Default flow categories:

| Flow | Default meaning |
|---|---|
| `request` | Synchronous request or command |
| `realtime` | Streaming or live telemetry |
| `batch` | Batch ingestion or scheduled transfer |
| `feedback` | Feedback, retraining, or response loop |
| `monitoring` | Metrics, logs, traces, or health data |
| `dependency` | Non-data dependency or association |

When two or more flow categories occur, the renderer adds an editable legend.

## 13. File Format and Portability

- The primary output is uncompressed diagrams.net XML stored in a `.drawio` file.
- The document declares itself as uncompressed to preserve inspectability and testability.
- Embedded images use data URIs.
- No absolute local filesystem paths appear in the document.
- No online URL is required to render a completed diagram.
- The file must open in current diagrams.net without import conversion.

## 14. Security and Privacy

- Output paths are restricted to the configured output directory.
- URL fetching is disabled by default and must be enabled explicitly.
- Online requests use HTTPS, timeouts, redirect limits, content-length limits, and media-type validation.
- SVG sanitization removes scripts, event attributes, external references, and `foreignObject` content.
- The server does not upload architecture specifications or generated diagrams.
- Tool errors must avoid exposing environment secrets or unrelated filesystem paths.

## 15. Error Handling

DrawArch returns structured errors containing:

- Stable error code
- Human-readable explanation
- Field or component identifier when applicable
- Suggested corrective action

Generation is atomic: a failed render or validation must not leave a partially written target file. Existing output files are not overwritten unless the tool call explicitly opts in.

## 16. Observability

V1 emits concise diagnostic messages to stderr only, preserving stdout for MCP transport. Diagnostics include tool name, elapsed time, asset resolution source, output file name, warning count, and stable error code. Architecture content and embedded asset bytes are not logged.

## 17. Acceptance Criteria

V1 is releasable when all of the following are demonstrated:

1. An MCP client can list and invoke all five V1 tools over stdio.
2. `create_drawio` generates a valid `.drawio` file for every supported layout and theme.
3. Generated nodes, groups, text, assets, and connectors are separate `mxCell` elements.
4. Bundled SVG assets are embedded as data URIs.
5. An online-provider fixture can resolve, sanitize, embed, and attribute an SVG without leaving a remote image link.
6. Animated edges contain diagrams.net flow animation style properties.
7. Multiple flow categories produce a legend.
8. Validation detects duplicate IDs, dangling references, unsafe external images, and malformed files.
9. Path traversal and accidental overwrite attempts are rejected.
10. Unit and integration tests pass, the TypeScript project builds, and a sample diagram is generated and validated.
11. Installation and MCP client configuration are documented.
12. The distributable ZIP excludes dependency folders, caches, secrets, and generated temporary files.

## 18. V2 Reference-Recreation Amendment

V2 adds a separate reference-image recreation pipeline while retaining every V1 tool:

- The connected MCP host's vision-capable LLM analyzes a user-provided image; DrawArch does not call or require another LLM API.
- The host supplies a typed absolute scene graph containing canvas, layers, z-order, confidence, editable shapes/text/assets/containers, and port-aware connectors with waypoints.
- Plans are persisted as immutable revisions. Rendering requires an HMAC approval token bound to the exact revision, and updates invalidate prior approvals.
- Asset modes include bundled icons, opt-in Iconify-compatible online icons, user data URIs, and approved HTTPS images.
- All images are sanitized, bounded, attributed, and embedded. HTTPS fetching revalidates DNS across redirects and rejects private/reserved targets.
- The renderer preserves exact coordinates and produces independent native Draw.io cells.
- Validation and structural comparison must meet the plan's minimum fidelity score before output is accepted.
- Generated `.drawio` bytes are returned directly as a portable MCP resource.
- The same eleven tools run locally over stdio or remotely over authenticated Streamable HTTP.

Pixel-level visual iteration is performed by the host vision model by inspecting output and revising the plan; DrawArch guarantees deterministic rendering and structural coverage, not cross-version pixel identity.

## 19. Success Measures

Initial success is measured by:

- Percentage of generated files opening without repair in diagrams.net.
- Percentage of nodes receiving an appropriate SVG without manual replacement.
- Connector overlap and node-intersection defect rate.
- Median time from prompt to usable `.drawio` file.
- Number of manual changes required before presentation use.
- Validation failure rate by category.
